## 重要纠正：v1 的“人工确认”不是硬保证

原项目已有的 `messaging` 技能里写的是“用户要发的，写好就发，不用先问”。
客服任务可能同时命中 `messaging` 与本技能，模型可能按 `messaging` 走。
所以 v1 的正确用法是：每次明确说“只起草不发”，并由你逐条确认；
真正能保证“不确认不发”的代码层硬拦截是 v2，必须改审批层并真机验证，
不能只靠技能文字。

## v1 做什么

- 微信巡查：读未读会话，汇总“谁、问了什么、什么时候”。
- 分类：咨询 / 下单 / 物流 / 售后 / 投诉 / 价格 / 账号付款 / 其他。
- 起草：只用 FAQ 模板里的内容回答，FAQ 没有的一律标“待确认”，不编造。
- 人工确认后才发送：用户没说“发”，就只停在起草。
- 转人工：退款、改单、补发、赔偿、价格承诺、投诉、情绪激烈、付款与验证码，
  一律停下汇总给用户。

## 已核对的上游事实

- 微信知识 ID 是 `wechat`，包名 `com.tencent.mm`，上游已标 `pace: careful`，
  即 Mika 在微信里本身就会放慢节奏、限制单任务换屏次数。这与客服版
  “低频、排队、人工确认”的定位一致，不是本版新加的。
- 上游微信知识目前只有 19 行左右，非常薄，所以客服 Skill 是本版的主要增量。

## v1 不做什么（刻意不做）

- 不默认自动发送、不群发、不主动加好友、不做营销。
- 不代付、不代退款、不改订单、不在微信里输密码和验证码。
- 不接订单系统、不查真实库存与物流（除非用户另外接官方接口，那是 v2）。
- 不承诺绕过微信风控。UI 自动化做微信客服本身就有被限制、封号的风险，
  详见原项目 docs/disclaimer.md。测试必须用测试号，不能用主号。

## 文件说明

- `core/src/main/resources/skills/wechat-customer-service/SKILL.md`
  客服技能，格式按原项目 docs/dev/knowledge-format.md 的 SKILL.md 格式。
  注意原项目规则：知识里只写事实，授权、确认、停止条件归通用准则和审批层，
  所以“必须人工确认”在技能里是“什么时候停下交给用户”，硬拦截是 v2 的代码层工作。
- `faq/faq-template.md`
  占位模板。用户填好自己的商家信息、发货、退换政策后，才算可用。
  填之前所有价格、库存、发货时间都只能答“待确认”。
- `core-cs/WeChatCsPolicy.kt`（草稿，未接入发送链路）
  纯逻辑分类器：把一条客户消息分成 DRAFT / ESCALATE，
  命中退款、投诉、价格承诺、付款、验证码等关键词就升级，并有手机号脱敏示例。
  v1 先以技能流程为准，这段代码不接入发送链路，不宣称已拦截；
  放进原项目时目标路径是 `core/src/main/kotlin/com/wangzan101/mika/core/cs/`。

## 使用流程（真机）

1. 在测试手机上装原版 Mika，先按原项目设置指南完成“设置手机操作”
   （无线调试配对、虚拟屏、无障碍），确认自检通过。
2. 把本版的 Skill 与 FAQ 放进对应 resources 位置后重新构建安装。
   构建前置：Android SDK、Gradle，见原项目 CONTRIBUTING。
3. 先填 FAQ，再用测试号做最小测试：
   - 1 个会话、1 条咨询类问题：巡查 -> 汇总 -> 起草 -> 你说“发” -> 发后读回核对。
   - 1 条退款类问题：应停下转人工，不直接发结论。
   - 1 条 FAQ 没有答案的问题：应标“待确认”，不编造。
4. 通过上面三条，才考虑扩大到少量熟客会话；仍不建议上主号、批量、高频。

## 还缺什么（需要用户提供）

- FAQ 实际内容：店铺名、客服时间、发货、快递、退换、价格口径。
- 测试手机型号与安卓版本（建议安卓 14+）、测试微信号（非主号）。
- 模型服务商与 API Key（走安全通道，不要发在聊天里）。
- 每天大概多少咨询、是否已有订单系统，决定 v2 是接官方客服 API 还是继续 UI 层。

## v2 方向（不包含在 v1）

- 代码层硬拦截：改 ApprovalPolicy 一类审批层，让微信对外发送也走确认，
  而不是只靠技能提示词。需要真机验证，不能只改文字就宣称安全。
- 官方通道：如果量上来，优先接企业微信客服 / 公众号客服官方 API，
  那条路不走 UI 自动化，风控与并发都更稳。
